- [x] `backend/src/routes/projects.ts` : le PUT recrée les tâches (`deleteMany` + `createMany`) au lieu de les mettre à jour — perte des IDs de tâches à chaque sauvegarde. **Corrigé** (branche `feat/backend-projects-put-fix`) : diff transactionnel update/create/delete, IDs stables vérifiés sur 2 PUT successifs.
- [x] `backend/src/routes/projects.ts` (POST et PUT) : les dates du body étaient passées brutes à Prisma — une date `yyyy-MM-dd` était rejetée (`Expected ISO-8601 DateTime`) et le handler crashait sans réponse (ECONNRESET). **Corrigé** : conversion factorisée dans `backend/src/utils/dates.ts` (`withDates`, appelée par les POST/PUT de projects.ts) **et** middleware d'erreur global `backend/src/middleware/errorHandler.ts` monté en dernier dans `index.ts` (+ `express-async-errors` pour capter les rejets async). Vérifié le 29 juillet 2026 : la case restait décochée alors que le code était corrigé.
- [x] **Dashboard : les dépenses fixes multi-sites disparaissaient dès qu'un périmètre était filtré.** Cette ligne décrivait auparavant une « asymétrie assumée — le Dashboard attribue le montant plein via le site principal ». C'était une **description fausse d'un vrai bug** : il n'y a pas de site principal. Pour une dépense multi-sites, le champ `site` contient le libellé concaténé (`"Clermont, Ussel, Mozac, …"`), et `isSiteInScope` fait un `filterContexts.includes(site)` — donc aucune correspondance, et la dépense était écartée **en totalité**, pas mal répartie. `Dashboard.tsx` n'utilisait ni `sites[]` ni `budgetDistribution`. Mesuré avant correctif : périmètre Clermont → consommé **0 €** au Dashboard contre **9 259 €** sur la ligne Clermont du Budget. **Corrigé le 29 juillet 2026** (`fix/dashboard-ventilation-depenses`) : ventilation par site avec la même source de parts que `Budget.tsx`. Vérifié après correctif — Clermont 9 259 €, Albi 9 259 €, et total sans filtre inchangé à 185 184 €.
- [ ] **Catalogue matériel intégralement dupliqué en base de production** : `GET /api/equipment` renvoie 32 lignes pour 16 noms uniques. Chaque paire a des ids différents et des `createdAt` espacés de quelques centaines de ms, tous le 2026-07-08 vers 22:07:32-33 → double exécution de la migration one-shot `migrateEquipmentIfNeeded` (`services/dataService.ts`), probablement deux onglets simultanés ou le double montage de React StrictMode. Effet visible : l'Inventaire affiche chaque équipement deux fois. **Nettoyage délicat** : les `EquipmentBooking` référencent un id précis via une FK — identifier l'exemplaire référencé et le conserver, ou réaffecter les réservations dans une transaction. Rendre la migration idempotente (un flag localStorage ne suffit pas si deux onglets démarrent en parallèle : viser une contrainte d'unicité en base). Découvert le 29 juillet 2026.
